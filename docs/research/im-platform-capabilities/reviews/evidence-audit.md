# OBCX IM/SNS Study — Wave 2 Evidence Audit

**Audit date:** 2026-08-17 UTC  
**Inputs:** `.pi/subagents/im-platform-capabilities/research-brief.md` and all ten Wave 1 Markdown artifacts.  
**Method:** Read-only artifact audit. No web-browsing tool was available, so URLs were assessed for form, authority, title/claim alignment, and internal consistency only. This is **not** exhaustive URL validation.

## Overall verdict

- **PASS:** Discord, Matrix, Telegram, Consumer WeChat
- **PARTIAL:** DingTalk, Lark/Feishu, OBCX current state, QQ, X
- **FAIL pending correction:** WeCom, because 12 of 18 registered sources are secondary mirrors and several central capability claims depend only on them.
- All ten artifacts separate product behavior from automation to some degree and include claim-to-source/file maps.
- The strongest boundary work is in QQ/OneBot, Telegram Bot API/TDLib, Matrix stable spec/MSC, Consumer WeChat/personal automation, and X legacy DM/XChat.
- The final capability matrix must not be generated by copying Wave 1 status labels mechanically. Status usage drifts between lanes, especially where a lane says `NATIVE` while also documenting permission, intent, role, plan, review, or implementation constraints.

## 2. Blocking findings for final integration

### B1. WeCom secondary-source dependence

Do not publish definitive WeCom cells based only on S2, S6, S8–S11, or S13–S18. Replace with official evidence or downgrade to `UNKNOWN`.

### B2. QQ active-send lifecycle evidence

Do not state that official active push is definitively withdrawn based on generic repository source S5. Final status must be `UNKNOWN`, disabled by default, until a direct current Tencent page or live approved-app entitlement confirms it.

### B3. Surface collision: WeChat Customer Service

`wave1/wechat.md` and `wave1/wecom.md` both cover 微信客服. The final model must have one canonical capability family, recommended:

```text
wechat.customer_service
```

with metadata noting administration/authentication through WeCom. Do not create two apparently independent matrix rows (`wechat.customer_service` and `wecom.kf`) for the same service.

### B4. Official QQ versus OneBot QQ

Maintain separate platform/surface keys:

```text
qq.official
onebot11.qq
```

OBCX’s current friend lists, arbitrary group moderation, message lookup, numeric IDs, cookies/CSRF, and private-account operations belong only to `onebot11.qq` unless independently supported by Tencent documentation.

### B5. Status-vocabulary normalization

The final matrix must apply one rule consistently:

- `NATIVE`: product and official API align without a material extra grant beyond ordinary authentication.
- `API_LIMITED`: permission, scope, role, intent, plan, review, region, scenario, window, implementation profile, or entitlement changes availability.
- `UNKNOWN`: evidence is absent, conflicting, inaccessible, or based only on an overview omission.
- `UNSUPPORTED`: an explicit boundary or sufficiently authoritative complete API/spec surface establishes that the capability is unavailable.

Do not copy ambiguous forms such as `UNSUPPORTED / UNKNOWN`, `NATIVE/API_LIMITED`, or `NATIVE with constraints` into one final cell. Split Product and API assessments or choose the more conservative API status.

## 3. Non-blocking findings

1. Every lane has a claim-to-source/file checklist, but several map broad groups of claims to monolithic references rather than direct headings.
2. GitHub `master`/repository-root links are mutable. QQ, DingTalk SDK, and some Matrix proposal evidence should use tags or commit permalinks.
3. Discord and X official Help pages were access-limited; they remain useful product-boundary evidence but should be visibly marked as such.
4. Negative claims frequently use “no endpoint found” as `UNSUPPORTED`. Where no explicit denial or complete authoritative catalog was checked, use `UNKNOWN`.
5. Commercial values are appropriately excluded from stable contracts in all lanes.
6. Region parity is generally not established and should remain capability metadata rather than a global platform claim.
7. Terminology for Webhook direction differs by platform. Final DTOs and prose should say:
   - “external system → platform posting endpoint”
   - “platform → adapter event callback”
   instead of relying solely on “incoming” or “outgoing.”

## 8. Source wording and freshness recommendations

1. Prefer wording such as:

   > “The audited official catalog did not expose a supported endpoint as of 2026-08-17.”

   over:

   > “The platform has no API.”

2. For every high-impact claim, retain:
   - exact page title
   - endpoint or heading
   - direct anchored URL where possible
   - access date
   - API/spec version
   - SDK tag or commit
   - entitlement/environment context

3. Replace GitHub repository-root and moving-branch links with immutable commit/tag permalinks, especially QQ S4/S5/S7 and SDK-derived evidence.

4. Distinguish authority precisely:
   - `SPEC — STABLE`
   - `SPEC — UNSTABLE MSC`
   - `OFFICIAL PRODUCT HELP`
   - `OFFICIAL DEVELOPER DOC`
   - `OFFICIAL SDK SOURCE`
   - `OFFICIAL — ACCESS-LIMITED`
   - `SECONDARY MIRROR`
   - `LOCAL CODE EVIDENCE`

5. An official domain does not automatically make a source current. Preserve deprecation notices, changelog dates, API generations, and contradictory older text.

6. Recheck the highest-volatility sources immediately before implementation:
   - QQ active sends, Gateway/Webhook lifecycle, Guild availability
   - Telegram 10.x modes and file/rate behavior
   - Discord privileged-intent review
   - Matrix stable-version/MSC transitions
   - WeChat and WeCom account entitlements/quotas
   - X access tier, Activity APIs, DM/XChat migration, and media
   - Lark/Feishu regional parity

7. Do not assign `HIGH` confidence to a negative claim supported only by omission from an overview or search result.

The Wave 1 set is structurally strong and generally disciplined about product/API boundaries. It is suitable for final synthesis only if the integrator:

1. keeps platform surfaces separately namespaced;

4. does not use OneBot as Tencent evidence or TDLib as Bot API evidence;
5. preserves Matrix stable/unstable distinctions;
6. resolves the WeChat Customer Service duplication;
7. replaces or downgrades WeCom’s secondary-only evidence; and
